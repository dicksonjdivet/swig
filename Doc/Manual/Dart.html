This chapter describes SWIG's support of Dart. Dart is a target language with Experimental status, see the Target Languages section for what that means. It can be used to wrap C and C++ libraries for use in Dart and Flutter applications.

41.1 Overview

The Dart module uses the dart:ffi library for calling C functions from Dart. SWIG generates a C/C++ wrapper file exporting a C function for each wrapped function, method, constructor, destructor and variable accessor, and a Dart library calling these C functions and providing Dart classes mirroring the C++ classes. The C/C++ wrapper file and the wrapped C/C++ code are compiled into a native shared library which is loaded when the Dart library is first used.

The generated Dart code only uses the dart: core libraries, no other Dart packages are needed. Dart 3.0 or later is required.

The Dart module is based on the C# module and the design is similar, so if you are familiar with the C# module, much of this chapter will look familiar. The main features are:

  • C functions, global variables and constants are wrapped in a module class. Variables are accessed using Dart getters and setters.
  • C++ classes are wrapped by Dart proxy classes. Single inheritance, static members, overloaded methods, default arguments and templates are supported.
  • C/C++ enums are wrapped by Dart enums.
  • C/C++ strings and std::string are converted to and from a Dart String.
  • std::vector is wrapped by a class implementing the Dart List interface.
  • C++ exceptions and other errors reported by the C/C++ code can be converted into Dart exceptions.
  • The C++ objects owned by Dart are deleted when the Dart proxy object is garbage collected, using a NativeFinalizer, or when dispose() is called.
  • Directors, so that C++ virtual methods can be overridden in Dart.

41.2 Preliminaries

41.2.1 Running SWIG

Suppose that you defined a SWIG module such as the following: 

/* File: example.i */
%module example

%inline %{
int gcd(int x, int y);
extern double Foo;
%}

To build the Dart module, run SWIG using the -dart option: 

$ swig -dart example.i

If building C++, add the -c++ option: 

$ swig -c++ -dart example.i

This creates the C/C++ wrapper file example_wrap.c or example_wrap.cxx and the Dart library example.dart. The Dart library is a single file containing all the Dart code generated for the module, it is named after the module name. The output directory for the Dart library can be changed with the -outdir option.

As the Dart module is experimental, SWIG issues a warning when it is used. The warning can be suppressed with the -w524 option.

41.2.2 Additional command line options

The following table lists the additional command line options available for the Dart module. They can also be seen by using: 

$ swig -dart -help
Dart specific options
-libname <name> Set the base name of the native library loaded by the generated Dart code, the default is the module name

41.2.3 Compiling the native library

The C/C++ wrapper file must be compiled and linked into a shared library together with the code being wrapped. For example, on Linux: 

$ swig -dart example.i
$ gcc -fPIC -c example.c example_wrap.c
$ gcc -shared example.o example_wrap.o -o libexample.so

No Dart or Flutter headers are needed to compile the wrapper. The shared library must be named after the module, or the name given by the -libname option, using the platform conventions: libexample.so on Linux and Android, libexample.dylib on macOS and example.dll on Windows. On iOS, the library is looked up in the example.framework framework, otherwise the symbols are looked up in the application itself, so the native code can be linked statically into the application. A library with a -d suffix, such as libexample-d.so, is also looked for, which is a common naming convention for debug builds.

The library is opened using DynamicLibrary.open() from dart:ffi, so it must be in a location where the operating system looks for shared libraries, for example a directory listed in the LD_LIBRARY_PATH environment variable on Linux. For Flutter applications, the native library is usually built and bundled as part of a Flutter plugin.

The library loading can be overridden by setting the static swigLibrary field of the intermediary class before the module is first used: 

import 'dart:ffi' as ffi;
import 'example.dart';

void main() {
  exampleFFI.swigLibrary = ffi.DynamicLibrary.open('/opt/example/lib/libexample.so');
  print(example.gcd(42, 105));
}

41.2.4 Using the generated Dart library

The generated Dart library is imported like any other Dart file: 

// File: runme.dart
import 'example.dart';

void main() {
  print(example.gcd(42, 105));
  example.Foo = 3.1415926;
  print(example.Foo);
}

$ LD_LIBRARY_PATH=. dart run runme.dart
21
3.1415926

41.3 Structure of the generated Dart code

The generated Dart library contains the following, in a single file named after the module:

  • The intermediary class, named after the module with an FFI suffix, such as exampleFFI. It loads the native library and contains a dart:ffi binding for each C function exported by the C/C++ wrapper. It also contains helper functions used by the rest of the generated code. The intermediary class name can be changed using the imclassname module option, for example, %module(imclassname="ExampleNative") example.
  • The module class, named after the module, which contains static methods, getters and setters wrapping the global functions, variables and constants.
  • A Dart class for each wrapped C++ class or C struct, called a proxy class, a Dart enum for each wrapped C/C++ enum and a type wrapper class for each type that SWIG does not know about, such as a pointer to a primitive type.

The names of the generated Dart classes and members are the C/C++ names, unless renamed with %rename. SWIG renames names which are Dart keywords or that clash with names used by the generated code and issues a warning when doing so. The generated code starts with ignore_for_file comments disabling the Dart lints about naming conventions.

When a module imports another module with %import, the generated Dart library imports the Dart library generated for the other module, so the Dart libraries of all the modules should be generated into the same directory.

41.4 C/C++ wrapping

41.4.1 Functions

Global functions are wrapped as static methods of the module class: 

%module example

int gcd(int x, int y);

abstract final class example {
  static int gcd(int x, int y) {
    final int ret = exampleFFI().gcd(x, y);
    return ret;
  }
}

The C/C++ types are mapped to the following Dart types:

C/C++ type Dart type
boolbool
charString containing a single character
signed char, unsigned char, short, unsigned short, int, unsigned int, long, unsigned long, long long, unsigned long long, size_tint
float, doubledouble
char *, char []String?
std::string, const std::string &String
enumDart enum
class by value and referenceproxy class
pointer to a classnullable proxy class, such as Shape?
other pointersnullable type wrapper class, such as SWIGTYPE_p_int?

A Dart int is a 64-bit signed integer, so unsigned 64-bit values above 0x7FFFFFFFFFFFFFFF are negative Dart integers. C/C++ integer values are truncated to the size of the C/C++ type as they are passed to the C/C++ code. The long and size_t types use the size of the native platform ABI.

A NULL pointer is a Dart null.

41.4.2 Global variables

Global variables are wrapped by a static getter and setter in the module class: 

print(example.Foo);
example.Foo = 3.1415926;

Read only variables, such as those wrapped using %immutable, only have a getter. A getter for a variable of class type returns a proxy class instance referring to the variable rather than a copy of the variable.

41.4.3 Constants

Constants created with #define or %constant are wrapped by static final variables, which are initialized on first access by calling a C wrapper function returning the C constant value: 

#define PI 3.14159

static final double PI = (() {
  final double ret = exampleFFI().PI_get();
  return ret;
})();

The %dartconst(1) directive can be used instead to generate a Dart const initialized with the C/C++ value. This only works if the C/C++ value is valid Dart code. The %dartconstvalue(value) directive can be used to specify the Dart value of a constant: 

%dartconst(1) BIG;
%dartconstvalue("0x7FFFFFFF") MAXINT;
#define BIG 1000
#define MAXINT 0x7FFFFFFFL

static const int BIG = 1000;
static const int MAXINT = 0x7FFFFFFF;

41.4.4 Enums

Named C/C++ enums are wrapped by Dart enums. The value of the C/C++ enum is available from the swigValue getter and the static swigToEnum method looks up the Dart enum value from a C/C++ enum value: 

enum Color { RED, BLUE = 10, GREEN };

final c = Color.BLUE;
print(c.swigValue);          // 10
print(Color.swigToEnum(11)); // Color.GREEN

The values of the enum items are computed by SWIG when possible, otherwise they are obtained by calling a C wrapper function. A Dart enum cannot be declared in a class, so an enum declared in a C++ class is named after the class and the enum, for example, the enum Shape::Kind is wrapped as Shape_Kind.

Anonymous enums are wrapped as integer constants in the module class or in the proxy class. Named enums can also be wrapped as integer constants using the %dartenum(simple) directive, or by including enumsimple.swg for all enums.

41.4.5 Classes

C++ classes and C structs are wrapped by Dart proxy classes. Member variables are wrapped by getters and setters, member functions by methods and static members by static members: 

class Shape {
public:
  Shape(double x, double y);
  virtual ~Shape();
  double x, y;
  virtual double area();
  static int nshapes;
};

class Circle : public Shape {
public:
  Circle(double x, double y, double r);
  virtual double area();
};

final c = Circle(1.0, 2.0, 10.0);
c.x = 3.0;
print(c.area());
print(Shape.nshapes);
Shape s = c;
print(s.area());  // calls Circle::area() as it is virtual

Single inheritance is supported. A class can only have one base class in Dart, so additional base classes are ignored and warning 784 is issued. Abstract C++ classes are wrapped by ordinary Dart classes as instances of them can be returned from the C++ code. Covariant return types are supported.

Nested classes are not supported by Dart, they are wrapped as top level classes, which means that nested classes with the same name in different classes need renaming to avoid a name clash.

A constructor renamed with %rename to a name other than the class name is wrapped as a Dart named constructor, as a Dart class has a single unnamed constructor: 

%rename(fromRadius) Circle::Circle(double r);

final c = Circle.fromRadius(10.0);

A wrapped operator() is renamed to call so that instances of the class can be called like a function in Dart. Other operators must be renamed with %rename to be wrapped.

41.4.6 Overloading and default arguments

Dart does not support overloading. Overloaded C/C++ functions, methods and constructors are wrapped by a single Dart function taking Object? parameters, which calls the matching C/C++ overload at runtime by checking the type of the arguments. The overloads are checked in the order of precedence used by SWIG for the C++ overload resolution rules. A Dart int argument also matches a double parameter. An ArgumentError is thrown if there is no matching overload. The return type is dynamic unless all the overloads return the same type. 

int value(int i);
double value(double d);

example.value(10);    // calls value(int)
example.value(10.5);  // calls value(double)

As several C++ types map to the same Dart type, some overloads cannot be distinguished in Dart. For example, value(int) and value(long) both take a Dart int. SWIG issues a warning and only wraps the first of these, use %rename to wrap the others with a different name.

Functions with default arguments are wrapped with optional positional parameters. A missing or null argument uses the C++ default value: 

void draw(int x, int y = 0, bool visible = true);

example.draw(1);
example.draw(1, 2);
example.draw(1, 2, false);

Constructors that are overloaded or have default arguments are wrapped by a Dart factory constructor.

41.4.7 Templates

Templates are wrapped as usual with SWIG, using %template to name the instantiations: 

template<class T> struct Pair {
  T first, second;
};
%template(IntPair) Pair<int>;

41.4.8 Pointers and references

Pointers to classes are wrapped by nullable proxy classes, references and objects passed by value are wrapped by non-nullable proxy classes. Passing null where a reference or an object by value is expected throws an ArgumentError.

Other pointers are wrapped by type wrapper classes named after the type, such as SWIGTYPE_p_int for int *. They can only be passed back to the C/C++ code.

41.5 Memory management

Each proxy class instance holds a pointer to the C++ object and a flag, swigCMemOwn, indicating whether the Dart instance owns the C++ object. C++ objects created from Dart by calling a constructor and objects returned by value are owned by Dart. Objects returned by pointer or reference are not owned by Dart, unless marked with %newobject.

An owned C++ object is deleted when the Dart proxy instance is garbage collected, using a NativeFinalizer calling the C++ destructor. As garbage collection is not deterministic, the C++ object can be deleted earlier by calling the dispose() method: 

final c = Circle(1.0, 2.0, 10.0);
print(c.area());
c.dispose();  // calls the C++ destructor

The proxy instance must not be used after calling dispose(). The proxy classes implement Finalizable from dart:ffi, so the Dart objects are not garbage collected while one of their methods is executing.

As for the other target languages, care is needed when a C++ object refers to another C++ object, as the Dart garbage collector does not know about this. For example, the proxy instance returned by a getter for a member variable of class type refers to memory within the containing C++ object, so it must not be used after the containing object is deleted.

41.6 Strings

char * and char [] are mapped to a nullable Dart String and std::string to a String, when std_string.i is included. The strings are converted to UTF-8 when passed to C/C++ and are converted from UTF-8 when returned to Dart. The C/C++ strings are copied in both directions, so the C/C++ code must not keep a pointer to a string passed to it from Dart after the call returns.

The (const char *STRING, size_t LENGTH) and (size_t LENGTH, const char *STRING) multi-argument typemaps are available to pass a Dart String as a pointer and a length in bytes, so that the string can contain null characters: 

%apply (const char *STRING, size_t LENGTH) { (const char *data, size_t len) };
size_t count(const char *data, size_t len);

print(example.count('a\u0000b'));  // 3

41.7 Exception handling

C++ exceptions and other errors cannot be propagated through dart:ffi calls. Instead, the C/C++ wrapper catches the C++ exception, records a pending exception and returns. The Dart code then checks for the pending exception and throws a Dart exception. The pending exception is stored in thread local storage.

C++ exceptions listed in an exception specification or with %catches are handled by the throws typemaps, as for the other target languages. The exception classes from the C++ standard library are converted into Dart exceptions when std_except.i is included. Other exceptions can be handled using %exception and SWIG_exception from exception.i: 

%include <exception.i>

%exception {
  try {
    $action
  } catch (std::exception &e) {
    SWIG_exception(SWIG_RuntimeError, e.what());
  }
}

The C/C++ code can also set a pending exception directly by calling SWIG_DartSetPendingException() followed by a return. The error codes and the Dart exceptions they are converted to are:

C error code SWIG_exception error codes Dart exception
SWIG_DartArgumentErrorSWIG_ValueErrorArgumentError
SWIG_DartArgumentNullErrorSWIG_NullReferenceErrorArgumentError
SWIG_DartRangeErrorSWIG_IndexErrorRangeError
SWIG_DartStateErrorStateError
SWIG_DartUnsupportedErrorUnsupportedError
SWIG_DartException, SWIG_DartOutOfMemoryErrorall the other codesSwigException

SwigException is a class generated in the Dart library, which implements Exception and has a message field holding the error message.

The Dart code only checks for a pending exception when the typemaps or features used by the wrapped function can set one. This is indicated by the canthrow attribute of the typemaps, see the C# exceptions section, as the Dart module uses the same mechanism. The %exception directive sets the canthrow attribute automatically.

41.8 STL support

The following STL library files are available:

  • std_string.i - std::string is converted to and from a Dart String.
  • std_vector.i - std::vector is wrapped by a class extending ListBase from dart:collection, so it can be used as a Dart List referring to the C++ vector.
  • std_pair.i, std_deque.i and std_except.i.
%include <std_vector.i>
%template(IntVector) std::vector<int>;
double average(const std::vector<int> &v);

final v = IntVector();
v.addAll([1, 2, 3, 4]);
print(v.where((i) => i > 2).toList());  // [3, 4]
print(example.average(v));                // 2.5

41.9 Directors

Directors make it possible to extend a wrapped C++ class in Dart and override its virtual methods, so that calls made from C++ to the virtual methods call the Dart methods. Directors are enabled using the directors module option and the director feature, as for the other target languages, see the Python directors section for an introduction: 

%module(directors="1") example
%feature("director") Callback;

%inline %{
class Callback {
public:
  virtual ~Callback() {}
  virtual int compute(int x) { return x + 1; }
};

class Caller {
  Callback *cb_;
public:
  Caller(Callback *cb) : cb_(cb) {}
  int call(int x) { return cb_->compute(x); }
};
%}

class MyCallback extends Callback {
  @override
  int compute(int x) => super.compute(x) * 10;  // super calls Callback::compute in C++
}

final cb = MyCallback();
final caller = Caller(cb);
print(caller.call(4));  // 50
cb.dispose();

The C++ director class calls the Dart methods through C function pointers created with Pointer.fromFunction from dart:ffi. This has the following consequences:

  • The C++ code must call the director methods from the thread running the Dart isolate which created the Dart object, and only while the Dart code is calling into the C/C++ code, for example, from a callback made during a call to a wrapped function. Calling a director method from another thread is not supported.
  • The Dart objects extending a director class are kept alive in a registry so that the C++ code can call them. They are not garbage collected and the C++ object is not deleted until dispose() is called.
  • A Dart exception thrown by a Dart method called from C++ cannot be propagated through the C++ code. Instead, the exception is reported as an uncaught error in the current zone and a default value, such as zero or null, is returned to the C++ code.
  • As Dart has no reflection, all the director methods are connected to the Dart methods. When a director method is not overridden in Dart, the C++ base class method is called, which also happens when the Dart method calls the base class method with super. A pure virtual method which is not implemented in the Dart class throws an UnsupportedError when called.

41.10 Typemaps

The Dart module uses the following typemaps. They are similar to the C# typemaps, which are listed in the Differences to the Java module section of the C# chapter, and to the Java typemaps documented in the Java typemaps section:

Typemap Description
ctypeC type used in the exported C wrapper functions
ffitypedart:ffi native type describing the C type, such as ffi.Int for int
imtypeDart type corresponding to the ffitype, used in the intermediary class
darttypeDart type used in the proxy classes, type wrapper classes and module class
dartinConversion of a Dart parameter from the darttype to the imtype, with optional pre, post and terminator attributes
dartoutConversion of the return value from the imtype to the darttype, the body of the Dart function
dartbase, dartinterfaces, dartinterfaces_derived, dartclassmodifiers, dartimports, dartcodeBase class, implemented interfaces, class modifiers, imports and additional code for the generated classes
dartbody, dartbody_derivedMain body of the proxy and type wrapper classes
dartdispose, dartdispose_derivedThe dispose method of the proxy classes
dartconstructInitializer list of the proxy class constructors
dartdirectorin, dartdirectoroutConversion of the director method parameters from the imtype to the darttype and of the return value from the darttype to the imtype, used by the Dart callbacks of the directors

The special variables available in these typemaps include $dartclassname, $*dartclassname, $&dartclassname, $dartinput, $imcall, $imclassname, $module, $owner and $excode, which are used in the same way as the corresponding C# special variables.

For example, the following typemaps pass a C++ Color struct as a Dart int holding the RGB value: 

struct Color { unsigned char r, g, b; };

%typemap(ctype) Color "int"
%typemap(ffitype) Color "ffi.Int"
%typemap(imtype) Color "int"
%typemap(darttype) Color "int"
%typemap(in) Color %{ $1.r = ($input >> 16) & 0xff; $1.g = ($input >> 8) & 0xff; $1.b = $input & 0xff; %}
%typemap(out) Color %{ $result = ($1.r << 16) | ($1.g << 8) | $1.b; %}
%typemap(dartin) Color "$dartinput"
%typemap(dartout) Color {
    return $imcall;
  }

The following pragmas can be used to customize the generated classes:

Pragma Description
%pragma(dart) imclassbase, imclassclassmodifiers, imclassinterfaces, imclasscodeBase class, class modifiers, interfaces and additional code for the intermediary class
%pragma(dart) modulebase, moduleclassmodifiers, moduleinterfaces, modulecodeBase class, class modifiers, interfaces and additional code for the module class
%pragma(dart) moduleimportsAdditional import directives for the generated Dart library
%pragma(dart) librarycodeAdditional top level code for the generated Dart library

The %proxycode directive adds code to a proxy class, as for the other target languages.

41.11 Known limitations

The Dart module is experimental and the following are not supported yet:

  • The nspace feature and the %interface family of directives for multiple inheritance.
  • Doxygen comments translation.
  • C++ operators other than operator(), unless renamed.
  • Many of the library files available for the other target languages, such as typemaps.i, cdata.i, std_map.i, std_shared_ptr.i and std_unique_ptr.i.
  • A Dart method cannot be overridden by a method with incompatible parameter types, so a C++ method hiding a base class method with different parameter types, including overloads of the base class method, can generate Dart code that does not compile.
